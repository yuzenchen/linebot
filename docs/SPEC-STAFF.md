# 員工打卡與薪資 bot 規格（SPEC-STAFF）

狀態：2026-11-12 定案。

## 1. 目標與非目標

### 目標

- 員工在 LINE 群組輸入「上班」「下班」打卡。
- 員工忘記打卡可申請補卡，管理員核准後才計入。
- 每月 1 日自動結算上個月的工時與應發薪資：管理員收到總表，員工私訊收到自己的明細。

### 決定（2026-11-12）

| 項目 | 決定 |
|------|------|
| LINE 帳號 | 新開員工專用官方帳號，同一份程式碼用 `BOT_PROFILE=staff` 執行，獨立容器與資料庫 |
| 打卡驗證 | 不驗證位置或裝置，信任員工 |
| 計薪 | 全部時薪制，每位員工可設不同時薪 |
| 加班 | 不分加班，所有時數都照時薪計 |
| 休息 | 不扣休息時間 |
| 補卡 | 員工申請、管理員核准 |
| 結算範圍 | 只算應發薪資，不算勞健保、勞退、所得稅 |
| 結算通知 | 管理員私訊收到總表；員工私訊收到自己的；群組不出現薪資 |

### 非目標（第一版）

- 加班費、休息日與國定假日加成、特休與請假。
- 勞健保、勞退、所得稅扣款與實發金額。
- 排班、遲到早退判定。
- 位置、QR code 或裝置驗證。
- 匯出檔案（CSV、Excel）。第一版只有 LINE 文字明細。
- 不使用 Claude 模型：所有指令都是固定格式，規則判斷，不產生 API 費用。

## 2. 架構

- 新 profile `staff`（`src/profiles/staff.ts`），沿用現有的 webhook、`Replier`、`push_log`、SQLite、migration、job queue。
- Pi 新增容器 `linebot-staff`：host port 8092、資料 `./data-staff`、設定 `.env.staff`、compose profile `staff`、對外 `https://linebot-staff.yuzen.tw`（Cloudflare Tunnel 加一個 Public Hostname，WAF Skip 規則同樣放行 `/webhook`）。
- 員工帳號不連 eshop、不連 Grok、不需要 `ANTHROPIC_API_KEY`。
- 只在 `STAFF_GROUP_IDS` 列出的群組動作。bot 被拉進其他群組時不回應，只在 log 記下 groupId，供設定使用。

## 3. 角色

- **管理員**：`STAFF_ADMIN_USER_IDS`（逗號分隔）。私訊 bot 下管理指令、核准註冊與補卡、收結算總表。
- **員工**：在 `employees` 表、狀態為啟用的人。管理員也可以同時是員工。
- 其他人：群組內的打卡指令回「尚未註冊，請輸入：註冊 你的名字」；其他訊息一律不回應。

## 4. 員工註冊

1. 員工在打卡群組輸入 `註冊 王小明`。
2. bot 在群組回「已送出註冊申請（E001 王小明），等待管理員核准」，並私訊每位管理員：「員工註冊申請 E001 王小明。核准請回：核准 E001 時薪 200」。
3. 管理員私訊 `核准 E001 時薪 200` → 員工啟用，時薪自核准當天起生效；群組回「王小明 已可打卡」。
4. 同一個 userId 重複註冊：已啟用回「你已註冊為 王小明」；申請中回「申請審核中」。
5. 管理員 `駁回 E001` → 刪除申請，群組不通知。

員工編號 `E001` 格式；顯示名稱以註冊時填的名字為準（不使用 LINE 暱稱）。

## 5. 打卡（群組）

- 群組訊息 trim 後**完全等於**「上班」或「下班」才算打卡，不需要 tag bot。其他群組訊息一律不回應。
- 時間以 bot 收到 webhook 的時間為準（台北時間），不接受員工自填時間（自填時間走補卡）。

| 情況 | 處理 | 群組回覆 |
|------|------|------|
| 上班，沒有進行中的班 | 開一筆班 | 「王小明 上班 09:02」 |
| 上班，已有進行中的班 | 不動 | 「王小明 已在上班中（09:02 起）」 |
| 下班，有進行中的班且未滿 16 小時 | 結束該班 | 「王小明 下班 18:05，本次 9 小時 3 分」 |
| 下班，沒有進行中的班 | 不動 | 「王小明 沒有上班紀錄，請用補卡：補卡 11/12 09:00 上班」 |
| 下班，進行中的班已超過 16 小時 | 不動，該班標記為「未下班」 | 「王小明 上班紀錄已超過 16 小時，請用補卡補下班時間」 |

- 跨午夜的班歸屬於**上班那天**。
- 60 秒內重複送同一指令視為重送，回第一次的結果、不重複記錄。

## 6. 補卡

- 格式：`補卡 11/12 09:00 上班`、`補卡 11/12 18:00 下班`。日期可寫 `11/12` 或 `2026/11/12`；省略年份時取最近一個不在未來的日期。群組或私訊都可以。
- 只能補上個月 1 日（台北日期）以後、且不晚於現在的時間（2026-11-12 由「31 天內」改為此規則，讓上個月在發薪日前都能補）。
- bot 回「已送出補卡申請 R001（11/12 09:00 上班），等待管理員核准」，並私訊每位管理員：「補卡申請 R001 王小明 11/12 09:00 上班。核准請回：核准 R001，駁回請回：駁回 R001」。
- 管理員核准 → 套用，並私訊申請人「補卡 R001 已核准」（申請人沒加 bot 好友時改在群組回）；駁回同理。
- 套用規則：
  - 補「上班」：在該時間開一筆班；若之後已有同一天未配對的「下班」補卡或已完成的班，按時間配對。
  - 補「下班」：結束該時間之前最近一筆未下班的班；找不到就核准失敗，回管理員「找不到可配對的上班紀錄」。
  - 套用後若同一員工的班互相重疊，核准失敗並說明原因，不寫入。
- 管理員可直接代補，免核准：`補卡 E001 11/12 18:00 下班`。

## 7. 工時與薪資計算

- 每一班的工時 = 下班時間 − 上班時間，以分鐘計，不扣休息、不取整。
- 未下班（沒有下班時間）的班不計入，結算時列為待處理。
- 時薪有生效日：`時薪 E001 210 自 12/1`（省略「自」= 今天起）。每一班套用上班當天有效的時薪。
- 應發薪資 = Σ（每班分鐘數 ÷ 60 × 該班時薪），**整月加總後**四捨五入到整數元。
- 一天工時超過 8 小時，或一週（週一到週日）超過 40 小時時，結算明細標註「超過 8 小時」「週超過 40 小時」，但不另計加班費（見 §11）。
- 時薪低於 `STAFF_MIN_HOURLY_WAGE`（預設 196）時，設定時薪的指令會警告，但仍允許設定。

## 8. 月結

- 計薪週期 = 依上班日期（台北時間）的自然月，算到每月最後一天。
- 發薪日 = 隔月 `STAFF_PAYDAY` 日（預設 15 日）。結算到發薪日之間是補卡與修正的緩衝期。
- 每月 1 日 09:00（台北時間）自動結算上個月：
  - **管理員私訊**：第一行「2026-11 薪資結算（12/15 發薪）」，接著每位員工一行「E001 王小明｜32 班｜168 小時 20 分｜NT$33,667」，最後一行合計。若有未下班的班、未處理的補卡申請、未核准的註冊，列在總表最後並說明「處理後可輸入：結算 2026-11 重新結算」。
  - **員工私訊**：自己的總時數、班數、應發金額、時薪（多段時薪分開列），發薪日（例如「12/15 發薪」），以及「明細請輸入：我的打卡 2026-11」。員工沒加 bot 好友時略過，並在管理員總表標註「未加好友，未通知」。
- 管理員可隨時輸入 `結算 2026-11` 重新計算並重發總表（不重發員工私訊，除非輸入 `結算 2026-11 通知員工`）。
- 每次結算寫一筆 `payroll_runs`（含當下計算結果快照），重新結算不覆蓋舊紀錄。

## 10. 資料模型（staff 資料庫；新表加進共用 migration 序列，三個 profile 的 DB 都會建表，只有 staff 使用）

- `employees`：id、user_id（唯一）、name、status（pending / active / disabled）、created_at、approved_at、approved_by。
- `wage_rates`：employee_id、hourly_wage、effective_from（日期）、created_by、created_at。
- `shifts`：id、employee_id、start_at、end_at（可空）、start_source、end_source（punch / correction / admin）、created_at、updated_at、deleted_at（軟刪除）。
- `correction_requests`：id、employee_id、kind（in / out / shift）、at、end_at（只有 shift 使用）、status（pending / approved / rejected / failed / cancelled）、reason、requested_by、group_id、shift_id、created_at、decided_by、decided_at（migration 010 重建，見 §15.6）。
- `payroll_runs`：id、month、run_at、triggered_by（schedule / userId）、result_json。
- `staff_reminders`：date（主鍵，台北日期）、sent_at（當天沒有符合項目時為空）、content_json（§15.5）。
- `staff_backups`：id、date、triggered_by、started_at、finished_at、ok、error、counts_json（migration 011，§16.6）。
- `audit_log`：每次管理員操作（核准、駁回、時薪、代補、修改、刪除、停用、結算）與員工取消補卡各一筆，含操作者與前後值。
- 沿用 `events`、`messages`、`push_log`、`users`。

保存：勞基法第 30 條要求出勤紀錄保存 5 年。打卡、補卡、時薪、結算資料一律不實體刪除（刪除打卡為軟刪除），`data-staff` 納入備份。

## 11. 法規提醒（使用者已知悉，第一版不處理）

- 依勞基法，一天超過 8 小時或一週超過 40 小時的部分應給加班費（前 2 小時至少 ×1.34、再 2 小時至少 ×1.67），休息日、國定假日另有規定。本系統第一版只標註，不計算。
- 時薪不得低於基本工資（`STAFF_MIN_HOURLY_WAGE` 預設 196，即 2026 年的基本時薪，請以勞動部公告為準）。
- 員工可要求查閱自己的出勤紀錄，`我的打卡` 指令即可提供。

## 15. 補卡改進（2026-11-12 定案）

核准、駁回結果的通知管道維持 §6：私訊申請人，私訊不到才發群組（考量群組 push 依人數計則數）。

### 15.1 核准失敗也通知申請人

- 現況只回管理員。改為同時通知申請人，管道同核准通知：「補卡 R001 無法套用：{原因}，請聯絡管理員」。
- 原因：找不到可配對的上班紀錄、和 S0123（11/12 09:00–18:00）重疊、超過 16 小時。
- 「下班」補卡因為找不到上班紀錄而失敗時，仍保留等待配對（§6 現有行為）；這種情況改說「等補上班紀錄後會自動配對」，不叫員工聯絡管理員。

### 15.2 管理員修改打卡時間

- 格式：`修改 S0123 上班 09:00`、`修改 S0123 下班 18:30`；可加日期：`修改 S0123 下班 11/13 02:00`。
- 不寫日期時：上班取該班原本的上班日期；下班取上班日期，若時間早於或等於上班時間則算隔天（跨午夜）。
- 修改未下班的班的「下班」= 幫它下班。
- 檢查：修改後上班早於下班、不超過 `STAFF_MAX_SHIFT_HOURS`、不晚於現在、不早於上個月 1 日、不和同一員工的其他班重疊；不通過就不寫入並說明原因。
- 寫入：該欄位來源改為 `admin`，`audit_log` 記 `edit_shift` 與前後值。
- 回覆：「已修改 S0123 王小明 11/12 09:00–18:30（9 小時 30 分）」。不通知員工（員工可用 `我的打卡` 查）。
- 修改已結算月份的班，回覆多一行「2026-11 已結算，請輸入：結算 2026-11 重新結算」。§6 代補與刪除打卡也比照加這行。
- 班號從 `打卡紀錄 E001 2026-11` 或 `刪除打卡 E001 11/12` 取得。

### 15.3 員工取消補卡申請

- 格式：`取消 R001`，群組或私訊都可以。
- 只能取消自己的、狀態為待審（pending）的申請。別人的回「找不到 R001」；已處理的回「R001 已核准／已駁回／已取消，無法取消」。
- 取消後狀態改為 `cancelled`，不通知管理員；管理員之後再核准或駁回會收到「R001 已取消」。
- 寫 `audit_log`（`cancel_correction`，操作者為員工 userId）。

### 15.4 一次補整班

- 格式：`補卡 11/12 09:00-18:00`（也接受 `~`）；管理員代補：`補卡 E001 11/12 09:00-18:00`。
- 結束時間早於或等於開始時間時算隔天（跨午夜）。
- 送出時檢查：開始不早於上個月 1 日、結束不晚於現在、時長不超過 `STAFF_MAX_SHIFT_HOURS`。
- 一筆申請 R001，管理員核准一次。套用：建立一個完整的班；和既有的班（含未下班的班）重疊就核准失敗，不寫入、不改既有的班。
- 回覆與通知文案顯示「11/12 09:00–18:00 整班」。
- 原本「上班」「下班」分開補的方式保留。

### 15.5 待審補卡提醒

- 每天 `STAFF_PAYROLL_CRON_HOUR`（預設 09:00）檢查一次，有下面任一情況就私訊每位管理員，同一天合併成一則：
  - 送出超過 3 天仍待審的補卡：「有 2 筆補卡待處理超過 3 天：R001 王小明 11/12 09:00 上班；R003 …。輸入：待處理」。
  - 發薪日前一天（每月 `STAFF_PAYDAY` − 1 日），上個月還有待審的補卡（不限天數）：「明天 12/15 發薪，2026-11 還有 1 筆補卡待處理：R004 …。處理後請輸入：結算 2026-11」。
- 沒有符合的就不發。一則最多列 10 筆，其餘寫「另有 N 筆」。
- 每天最多發一次：先寫 `staff_reminders`（日期唯一）再發送，重啟不重發；容器在 09:00 沒開時，當天稍後補發，隔天不補前一天的。
- 不自動過期、不自動駁回。

### 15.6 資料模型（migration 010）

- `correction_requests`：
  - `kind` 加 `shift`（整班）。
  - 新增 `end_at`（只有 `shift` 使用）。
  - `status` 加 `cancelled`。
  - SQLite 不能改 CHECK，以重建表方式遷移，保留 id 與既有資料。
- 新表 `staff_reminders`：date（主鍵，台北日期）、sent_at、content_json。

### 15.7 指令總表增補

| 指令 | 誰 | 位置 |
|------|------|------|
| 補卡 11/12 09:00-18:00 | 員工 | 群組或私訊 |
| 取消 R001 | 員工 | 群組或私訊 |
| 補卡 E001 11/12 09:00-18:00 | 管理員 | 私訊 |
| 修改 S0123 上班 09:00、修改 S0123 下班 11/13 02:00 | 管理員 | 私訊 |

`說明` 的員工與管理員段落同步更新。

### 15.8 完成定義

- [ ] 整班補卡：申請 → 核准 → 一個完整的班；跨午夜正確；重疊時失敗且不動既有資料。
- [ ] 取消：自己的待審可取消；別人的、已處理的不行；取消後管理員核准回「已取消」。
- [ ] 修改：上班、下班、跨午夜、幫未下班的班下班；重疊、超時、未來時間被擋；`audit_log` 有前後值。
- [ ] 核准失敗時申請人收到原因。
- [ ] 提醒：超過 3 天的待審、發薪日前一天兩種情況；同一天只發一次；重啟不重發。
- [ ] 既有測試全過，客服與管理端 bot 行為不變。

## 16. 每日備份到 Google 試算表（2026-11-12 定案；同日改為每天 01:00）

目的：出勤與薪資資料須保存 5 年，目前只在 Pi 的 SD 卡上。每天把完整資料寫到使用者的 Google 試算表，作為異地備份，也方便直接檢視。做法沿用 JOJO 專案：試算表內的 Apps Script 網頁應用程式接收 POST。

### 16.1 時機

- 每天 `STAFF_BACKUP_HOUR`（預設 1，即 01:00 台北時間）執行一次，備份到當下為止的全部資料；每月 1 日 09:00 的月結會在 2 日 01:00 的備份中出現。沿用月結排程的檢查方式（啟動時與每 5 分鐘），同一天成功過就不再跑，重啟不重跑；容器在 01:00 沒開時當天稍後補跑，不補前幾天。
- 管理員可隨時私訊 `備份` 立即執行（第一次設定完用來測試，或重要修改後手動備份）。
- 未設定 `STAFF_BACKUP_SHEET_URL` 時整個功能關閉，`備份` 回「尚未設定備份試算表」。

### 16.2 內容（每次完整覆寫，不是增量）

每個分頁第一列是標題，時間一律轉成台北時間 `2026-11-12 09:00`。

| 分頁 | 欄位 |
|------|------|
| 員工 | 編號、名字、狀態、LINE userId、申請時間、核准時間、核准者 |
| 時薪 | 員工編號、名字、時薪、生效日、設定者、設定時間 |
| 打卡 | 班號、員工編號、名字、上班、下班、分鐘、上班來源、下班來源、刪除時間、建立時間、更新時間 |
| 補卡 | 編號、員工編號、名字、類型、時間、結束時間、狀態、原因、申請者、群組、班號、申請時間、處理者、處理時間 |
| 結算 | 結算編號、月份、執行時間、觸發者、員工編號、名字、班數、分鐘、應發金額（每次結算每位員工一列，從 `payroll_runs` 快照展開） |
| 操作紀錄 | 編號、操作者、動作、對象、修改前、修改後、時間 |
| 備份資訊 | 備份時間、觸發者（排程或管理員）、資料庫版本、各分頁筆數 |

- 已軟刪除的打卡也寫入（「刪除時間」欄有值），與資料庫一致。
- 不含 LINE 金鑰、`events`、`messages`、`push_log`。

### 16.3 防止覆蓋掉好的備份

- Apps Script 寫入前比對：任何分頁的新筆數少於試算表現有筆數就拒絕寫入，回「筆數減少」。正常營運只會增加（打卡刪除是軟刪除），筆數減少代表資料庫可能出問題。
- 確定要覆寫時（例如手動清理過測試資料），管理員私訊 `備份 強制`。
- Google 試算表本身的版本記錄可還原到之前的任何一次備份。

### 16.4 安全

- 網址視同密碼，只放 Pi `.env.staff`。另外帶 `STAFF_BACKUP_TOKEN`，Apps Script 比對指令碼屬性中的同一個值，不符就拒絕。
- 試算表只分享給使用者本人（含員工 LINE userId 與薪資）。
- log 不印網址與 token。

### 16.5 結果通知

- 成功：只記 log 與 `staff_backups`，不發 LINE（省推播）；手動 `備份` 時回覆「備份完成：員工 3、打卡 120、補卡 8…」。
- 失敗（網路錯誤、token 不符、筆數減少）：私訊每位管理員一次「11/13 每日備份失敗：{原因}。處理後可輸入：備份」。排程失敗後每小時重試一次，到當天成功為止；連續失敗（含跨日）只在第一次通知，之後恢復成功時再私訊「備份已恢復」。

### 16.6 資料模型與設定

- 新表 `staff_backups`：id、date（排程用的台北日期，手動為空）、triggered_by、started_at、finished_at、ok、error、counts_json。
- `.env.staff` 新增 `STAFF_BACKUP_SHEET_URL`、`STAFF_BACKUP_TOKEN`（兩者都填才啟用）、`STAFF_BACKUP_HOUR`（預設 1）。
- 新增 `docs/STAFF-BACKUP.md`：建立試算表、貼上 Apps Script、設定 token、部署網頁應用程式的步驟，與 Apps Script 原始碼。

### 16.7 完成定義

- [ ] 每天 01:00 自動備份一次；重啟不重跑；失敗每小時重試，連續失敗只通知一次，恢復時通知。
- [ ] `備份`、`備份 強制` 可手動執行；未設定時回提示。
- [ ] 筆數減少時拒絕覆寫並通知；token 不符被拒。
- [ ] 試算表七個分頁內容與資料庫一致（正式環境實測一次）。
- [ ] 測試用 mock fetch 與臨時 SQLite，不打真實 Google。

## 17. 批次補卡與批次核准（2026-11-12 定案）

一次最多 12 筆。單筆的寫法與回覆完全不變。

### 17.1 員工多行補卡

- 一則訊息多行，每行一筆補卡（§6、§15.4 的任何寫法），空白行略過。群組或私訊都可以。
- 先檢查格式：任何一行不是補卡指令或格式錯，整則不處理，回「第 2 行格式不對：…」並附格式範例。超過 12 行回「一次最多 12 筆，請分開送」，整則不處理。
- 格式都對時逐行送出申請，每行各自檢查（未來時間、超出範圍、超過 16 小時、重複申請）；通過的建立申請，沒通過的不建立。同一則訊息裡完全相同的兩行，第二行算重複。
- 回覆一則彙總，一行一筆：「R004 11/10 09:00–18:00 整班 已送出」「11/01 09:00 上班：只能補上個月 1 日以後的打卡」，最後「共送出 3 筆，等待管理員核准」。
- 管理員只收到一則通知，列出這次建立的全部申請，最後「核准請回：核准 R004 R005 R006，或：核准全部」。

### 17.2 管理員多行代補

- 私訊多行 `補卡 E001 …`，每行可以是不同員工；格式檢查與 12 筆上限同 17.1。
- 依行序逐筆直接套用（後面的行看得到前面行寫入的班），回覆一行一筆結果與失敗原因；有已結算月份時，最後加一行重新結算提示（同 §15.2）。

### 17.3 批次核准、駁回

- `核准 R004 R005 R006`、`駁回 R004 R005`：編號以空白、逗號或頓號分隔，最多 12 個，重複的編號只算一次。
- `核准全部`：核准最早送出的待審申請，最多 12 筆；還有剩時最後加「另有 N 筆待審，可再輸入：核准全部」。沒有待審回「目前沒有待審的補卡」。
- 依補卡時間由早到晚處理（讓同一員工的上班、下班能配對），每筆各自成功或失敗，回覆一行一筆。
- 員工通知合併：同一位申請人的結果合成一則（管道同 §6：私訊，私訊不到才發申請時的群組；同一位申請人的申請來自不同群組時，各群組各發一則）。
- 核准失敗通知申請人的文字同 §15.1，合併在同一則。

### 17.4 不做

- `駁回全部`、批次取消、批次修改打卡。
- 註冊核准（`核准 E001 時薪 200`）不支援多筆。

### 17.5 完成定義

- [ ] 多行補卡：全部成功、部分因規則被擋、任一行格式錯整則不處理、超過 12 行、空白行、同訊息重複行。
- [ ] 管理員只收到一則彙總通知。
- [ ] 多行代補依行序套用，可混不同員工。
- [ ] 批次核准與駁回：分隔符號、重複編號、超過 12 個、不存在或已處理的編號、上下班配對、每位申請人只收一則。
- [ ] `核准全部`：最多 12 筆、剩餘提示、沒有待審。
- [ ] 單筆行為與既有測試不變。
